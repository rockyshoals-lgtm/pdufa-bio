# 🔴 The real bug — `/api/v1/events` diverges from the rendered site

This is the same API/page split I flagged for MNKD on 2026-07-25, still unresolved and now broader. Fresh origin responses (`x-vercel-cache: MISS`, `age: 0` — not a cache artifact):

| Event | Rendered site (correct) | `/api/v1/events` (wrong/stale) |
|---|---|---|
| OTLK bevacizumab | **Approved, 2026-07-24** | `status:"Awaiting", outcome:null` |
| CAPR AdComm 07-29 | **Held, 9-3 against** | `status:"Scheduled", updated_at:2026-07-11` |
| `updated_at` mode | site is current | 326 rows stamped `2026-07-11` |

### Why it matters (two concrete consequences)
1. **`/llms.txt` sends ChatGPT/Perplexity/Gemini to this API.** They read "OTLK: awaiting decision" for a drug that's been approved for six days. The rendered page is right; the machine-readable surface is wrong — and the machine surface is what AI quotes.
2. **The "Data through" freshness badge keys off the API's `updated_at` mode** (= Jul 11), so the badge reads "Data through Jul 11" **even though the site itself is current.** The site is *underselling its own freshness* because the badge is fed the stale API timestamps.

### The fix
The rendered pages and the API read from different places (or the API serializer isn't re-run on decision capture). **Make `/api/v1/events` a faithful mirror of the decision data the pages already have:** propagate `outcome` + `decision_date` to the API's PDUFA records, refresh AdComm status/vote in the API, and update `updated_at` when a record changes so the badge reflects true currency. This is the MNKD-07-25 fix extended to OTLK/AdComms/timestamps.
