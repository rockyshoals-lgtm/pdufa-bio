# 🔴 P0-A — The site is showing FDA decisions for three companies that have nothing to do with the drug

**This is the most serious accuracy defect found in this engagement.** It is live, it is on the homepage, and it is exactly the failure mode a "most accurate calendar in existence" cannot have.

`/api/v1/events` and the homepage both list the **2026-08-17 Keytruda + Padcev** perioperative MIBC decision under **six tickers**:

| Ticker | Company | Legit? | market_cap | tier | indication string |
|---|---|---|---|---|---|
| MRK | Merck | ✅ Keytruda sponsor | 308,900,939,584 | Large | `Muscle-invasive bladder cancer (MIBC)` |
| PFE | Pfizer | ✅ Padcev co-owner | 138,211,420,000 | Large | `Muscle-invasive bladder cancer (MIBC)` |
| ALPMY | Astellas | ✅ Padcev co-owner | 23,629,782,883 | Large | `Muscle-invasive bladder cancer (MIBC)` |
| **BNTX** | **BioNTech** | 🔴 **NO** | **null** | **null** | `Perioperative muscle-invasive bladder cancer ` |
| **CTMX** | **CytomX** | 🔴 **NO** | **null** | **null** | `Perioperative muscle-invasive bladder cancer ` |
| **EVAX** | **Evaxion** | 🔴 **NO** | **null** | **null** | `Perioperative muscle-invasive bladder cancer ` |

**Verified against primary sources.** The Aug 17 2026 target action date is real — it is Merck's sBLA for Keytruda/Keytruda QLEX + Pfizer-Astellas' Padcev, based on **EV-304 / KEYNOTE-B15**. BioNTech, CytomX and Evaxion are **not parties to this application**. Evaxion is a Danish AI-vaccine microcap; it has no bladder-cancer BLA.

### The bug is diagnosable from the payload itself
The three bogus rows share a **fingerprint the three real rows don't have**: `market_cap = null`, `market_cap_tier = null`, and a **different indication string with a trailing space** (`Perioperative muscle-invasive bladder cancer ` vs `Muscle-invasive bladder cancer (MIBC)`).

**They came from a different source row and were joined in on drug/indication text, not on sponsor.** That is a many-to-many join with no sponsor key.

### It is systematic, not a one-off
Same-date + same-drug fan-out across multiple tickers:

| Date | Drug | Tickers | Assessment |
|---|---|---|---|
| 2026-08-17 | Keytruda + Padcev | ALPMY, BNTX, CTMX, EVAX, MRK, PFE | 🔴 **3 of 6 wrong** |
| 2026-09-26 | zilurgisertib | INCY, **MIRM** | 🔴 zilurgisertib is Incyte's. Mirum unrelated. |
| 2026-08-25 | Ziihera (zanidatamab) | JAZZ, ZYME, **ONC** | 🟠 Jazz + Zymeworks legit (partners). Verify ONC. |
| 2026-09-18 | Zidesamtinib | NUVL, **RPRX** | 🟠 Nuvation legit. RPRX is a royalty holder — defensible but should be labelled, not listed as the sponsor. |
| 2026-06-18 | Tebipenem | GSK, SPRO | ✅ Correct — GSK licensed from Spero. |

### The fix
1. **Join on sponsor/applicant, never on drug or indication text.**
2. **Block the null-mcap signature at publish:** a PDUFA row whose ticker resolves to no market cap while a sibling row on the same date/drug has one is a join artifact. Fail the build.
3. **Partner/royalty rows need a `role` field** (`sponsor` / `partner` / `royalty`) and should render as *"PFE — partner"*, not as an independent decision. Six identical rows on one date also inflates "72 upcoming PDUFAs."
4. **Add these three to `/corrections`.** They were publicly visible.

```python
# tests/test_no_ticker_fanout.py
import pandas as pd, sys
d = pd.read_csv('catalysts_out/catalysts_public.csv')
p = d[d.type=='PDUFA']
errs=[]
for (dt,drug), g in p.groupby(['date','drug']):
    if len(g)>1 and g.market_cap_usd.notna().any() and g.market_cap_usd.isna().any():
        errs.append(f'FATAL join artifact {dt} {drug}: no-mcap tickers '
                    f'{sorted(g[g.market_cap_usd.isna()].ticker)} alongside resolved ones')
if errs: print('\n'.join(errs)); sys.exit(1)
```

# 🔴 P0-B — The API asserts day-precision on 299 dates it does not have. The site does not.

**All 299 readouts in the API fall on the 15th of the month. Every one is tagged `"date_precision":"day"`.**

```json
{"id":"readout_agio_2026-06-15","date":"2026-06-15","date_precision":"day", ...}
```

Day-of-month distribution, readouts: **`15` → 299. That is the entire distribution.** (PDUFA dates, by contrast, span 26 distinct days — those are real.)

**The rendered page gets this exactly right** and deserves credit:
> *"Dates are **estimated primary-completion windows** from ClinicalTrials.gov, not fixed announcements — they shift."*
> and every row reads **`AGIO · Jun 2026 (est.)`** — month precision, explicitly flagged.

The page is honest. **The API contradicts it.** A consumer — including an LLM, and `/llms.txt` is live — reads `2026-06-15` + `date_precision: day` and publishes *"AGIO reports June 15."* That date does not exist.

**Fix:** set `date_precision:"month"` for these 299, emit `date_month:"2026-06"`, and keep `date` as the sortable midpoint documented as such. **The API must not claim more precision than the page.** This is the same class of defect as the fabricated conference dates — a month estimate stamped as a hard day.
