## 3. 🆕 New issues (on surfaces that are new or newly healed)

### 3a. `/readouts` shipped — but it leaks users and SEO straight to ClinicalTrials.gov (high)
The phase-readout calendar is live and correctly **facts-only** (no scores/PoA — good). But:
- **Every row links off-site directly to `clinicaltrials.gov/study/NCT…`** — there are **no on-site `/readout/…` pages** (grep: 0). You're dumping the visitor (and your link equity) straight off your domain. The PDUFA calendar links to on-site `/pdufa/<slug>` pages; readouts should mirror that — build `/readout/[ticker-nct]` detail pages (drug, indication, trial design, phase, then a link *out* to CT.gov). This is the difference between owning the "[drug] phase 2 readout date" long tail and donating it to NIH.
- **Many rows have no drug name** — bare "`- —`" (e.g. "BMY · 2026-06-25 - — Advanced Cancer", "KPTI — Lymphoma", lots in Jul/Aug). Backfill the intervention name from CT.gov or suppress the empty dash; right now it reads unfinished.
- **Healthy-volunteer / Phase-1 PK noise** — rows like "Healthy Volunteers", "Healthy Participants", "Healthy" aren't market-moving readouts and dilute the signal. Filter or de-emphasize; lead with Phase 2/3 efficacy readouts.
- **1st-of-month placeholder pile** — huge clusters on `2026-07-01`, `2026-08-01` are clearly "month estimate → defaulted to the 1st." The page caveats it well ("estimated… they shift"), but visually bucket them like the PDUFA "Q4 (est.)" treatment ("July 2026 (est.)") so it doesn't look like hard dates.

### 3b. Residual data-quality dupes on the calendar (med)
- **VRDN double-listed:** `/calendar` shows **two** VRDN rows on 2026-06-30 — "Veligrotug (VRDN-001)" and "VRDN-001" — same ticker, company, date, indication (TED), same drug. The cross-ticker dedup ("GSK / SPRO") doesn't catch **same-ticker alias variants** (brand vs code name). The live `/api/data` has one VRDN, so it's the **static build's** dataset that's stale/duped — re-dedup at build time on (ticker + normalized-drug + date).
- **GSK tebipenem shown approved *and* pending:** `/api/data` has GSK 06-18 **Approved** ("Utebzi (tebipenem pivoxil) approved"), yet `/calendar` also lists "GSK · 06-30 Tebipenem pivoxil — cUTI" as upcoming. Same product appearing as both decided and pending erodes trust on a facts-first calendar — reconcile.

### 3c. Decision-outcome latency (med — it's your core promise)
`ACHV`'s PDUFA was **2026-06-20**; as of 2026-06-24 `/api/data` still shows `outcome:"pending"` (it renders "Date passed — outcome unknown"). A 4-day lag tagging the outcome on a tracked catalyst is a freshness gap for a product whose whole value is being current on decisions. Tighten the post-date outcome capture (even a daily 8-K/Drugs@FDA sweep on just-passed dates).

### 3d. Nav is overflowing (low/med)
Top nav is now **9 items**: Calendar · Readouts · Devices · Decisions · Approvals/yr · Trial odds · Learn · Research · Methodology. On mobile that wraps badly. Group into ~4: **Calendar ▾** (PDUFA/Readouts/Devices), **Decisions ▾** (Approvals/CRLs/Approvals-by-year), **Learn ▾** (Learn/Research/Trial-odds/Methodology/Sources), + the brand. (Also: `/devices` is brand-new and unaudited — confirm it carries the same disclaimers and isn't scope-creeping the PDUFA focus.)

### 3e. "LIVE" still overstates (carry-over W6, now confirmed at the header)
`/api/data` still returns `cache-control: s-maxage=16000` (≈4.44h) — so the "~5×/day" is the cache TTL, and data shown can be up to ~4.4h old (plus ORATS ~15-min vendor delay) while labeled "LIVE." `/sources` honestly says "snapshot, not a live tick" — make the dashboard header match: **"Snapshot · updated `refreshed_utc` · ~5×/day."** (Builder noted crons exist in vercel.json; fine — but the freshness ceiling is still the s-maxage, so reconcile the wording, not necessarily the mechanism.)
